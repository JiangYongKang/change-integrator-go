# 变更集成引擎（change-integrator）

面向持续集成的变更集成引擎：接收一组待入主干的变更（提交或补丁），在本地基准上
做**预演（dry-run）**与**实际应用（apply）**，给出可复现、可解释的结论，并支持
**中断续跑**与**重复提交**。

- 纯 Go 标准库实现，无第三方依赖。
- 包：`pkg/integrator`；命令行：`cmd/integrator`。

---

## 1. 变更模型

每个提交或补丁都被归一为统一模型 `Change`（见 `pkg/integrator/change.go`）：

| 字段 | 含义 |
| --- | --- |
| `id` | 变更的稳定唯一标识（如提交哈希）。为空时引擎按内容指纹生成 `c<指纹前缀>` |
| `depends` | 显式依赖的其它变更 ID，用于声明先后关系 |
| `message` | 描述信息，仅用于日志/报告展示 |
| `files[]` | 文件补丁列表，同一变更内不允许对同一路径重复打补丁 |

文件补丁 `FilePatch`：

- `path`：目标文件相对路径，统一以 `/` 分隔；禁止绝对路径与 `..` 越界。
- `isNew` / `isDelete`：新建 / 删除标记，二者互斥。
- `hunks[]`：unified-diff 风格补丁块，每行为三种操作之一：
  - `" "`（context）上下文行，必须与基准逐字一致；
  - `"+"`（add）新增行；
  - `"-"`（del）删除行。
- `oldStart/oldLines/newStart/newLines` 为块位置与跨度，必须与行内容计数一致，
  否则在归一阶段以 `invalid-change` 拒绝。

### 内容指纹与变更集身份

- **内容指纹（Fingerprint）**：对消息与全部补丁行规范化后做 SHA-256，与 `id` 无关。
  同一变更集内若出现不同 ID 但指纹相同的两项，判为**重复提交**。
- **变更集身份（SetID）**：由集合内全部 `(id, 指纹)` 对排序后派生，标识“同一变更集”。
  续跑状态只在 SetID 匹配时被承认；属于其他变更集的状态会被忽略（日志明确说明），
  避免跨集误跳过。

### 输入 JSON（CLI）

```json
{
  "changes": [
    {
      "id": "c1",
      "message": "replace a with A",
      "depends": [],
      "files": [
        {
          "path": "f.txt",
          "isNew": false,
          "isDelete": false,
          "hunks": [
            {
              "oldStart": 1, "oldLines": 1,
              "newStart": 1, "newLines": 1,
              "lines": [
                {"op": "-", "text": "a"},
                {"op": "+", "text": "A"}
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

## 2. 归一与顺序判定规则

顺序判定（`resolveOrder`）在任何应用动作之前完成。以下任一情况都会以
**可区分的拒绝原因**明确拒绝整个变更集，**不静默丢弃、不按到达顺序硬套**：

| 拒绝原因（RejectReason） | 触发条件 |
| --- | --- |
| `invalid-change` | 空变更集、无补丁、路径非法/越界、块跨度与行不一致、同变更内路径重复等 |
| `duplicate` | 同一 `id` 出现多次；或不同 `id` 但内容指纹相同（重复提交） |
| `missing-dependency` | `depends` 引用了变更集之外（不存在）的变更 |
| `order-undecidable` | 依赖成环；或两个变更作用于同一文件，但二者之间**没有任何（传递）依赖关系**给出先后依据 |

关键原则：

1. **不按到达顺序猜测。** 两个无依赖关系的变更改同一文件时，即使按输入顺序
   “能套上去”，也判 `order-undecidable`，且结论与提交顺序无关。
2. **显式依赖给出先后依据。** A、B 改同一文件且 `B.depends = [A]`（或存在
   传递依赖路径）时，顺序确定为 A → B。
3. **确定性破平。** 互不重叠的独立变更没有先后歧义，在拓扑排序的同层就绪节点中
   按 ID 字典序稳定选择；因此最终顺序完全由变更内容与依赖决定，与提交顺序无关、
   可复现。

判定结果（应用顺序 `Order`）会写入日志，格式形如：
`[apply] 变更集 ab12…：归一 3 项，判定顺序 [c1 c2 c3]`。

## 3. 冲突处理规则

按判定顺序逐个变更、逐文件、逐 hunk 应用到内存文件视图。

### 3.1 hunk 定位（严格，不猜测）

1. 先尝试 `oldStart` 声明位置精确匹配（允许此前插入导致的整体漂移，但不会回溯到
   已被前一个 hunk 消费过的区间）。
2. 声明位置不匹配时，在剩余允许区间内扫描：
   - **唯一匹配** → 漂移到该位置应用；
   - **多个候选** → 判冲突（定位歧义），绝不任选其一；
   - **无匹配** → 判冲突，并定位到第一个不一致行。
3. 纯插入块（无旧侧行）以 `newStart` 为插入点。

### 3.2 冲突位置与来源

每个冲突产生一条 `ConflictLocation`：

- `change`：冲突的变更 ID；
- `path` / `hunkIdx` / `line`：文件、块序号、基准行号（1 起）；
- `detail`：人类可读原因（如“期望 X，实际 Y”“多处相同匹配，定位歧义”）；
- `sourceChange`：导致该行无法匹配的**来源变更 ID**；为空表示冲突源于基准内容本身。
  来源信息通过对每个文件每一行维护 owner 标记得到（该行最近由哪个变更落盘）。

### 3.3 不回退、不重复应用

- 一个变更的任一文件补丁冲突时，该变更标记为 `conflict`，**整变更不应用**；
  处理在该顺序位置停止，后续变更保持“未处理”（续跑时从正确位置继续）。
- 此前已干净应用的变更**不回退、不撤销**，保持落盘。
- 失败的补丁不会就地修改文件视图（函数式返回新视图），保证现场一致。

## 4. 预演（dry-run）与应用（apply）

两种模式共用同一条执行路径：同一归一、同一顺序、同一严格匹配/冲突判定、同一
续跑状态识别。对**同一基准与同一续跑状态**，两种模式产出的
`applied / skipped / conflict` 三个集合**完全一致**。

| | dry-run | apply |
| --- | --- | --- |
| 归一 / 顺序判定 | 是（失败即拒绝） | 是 |
| 在内存视图上应用并定位冲突 | 是 | 是 |
| 读取续跑状态并识别已应用项 | 是 | 是 |
| 修改基准文件 | **否** | **是** |
| 写入续跑状态文件 | **否** | **是** |
| 结论中的 `applied` 含义 | “预演通过，若执行 apply 将应用” | “已真正落盘应用” |

因此可以先 `dry-run` 获取可复现结论，再用同一变更集 `apply`，两者结论一致。

### 中断与重复提交（状态先行 + 应用后镜像）

续跑状态记录在 `.integrator-state.json`（可用 `-state` 改路径），包含：

- SetID 与按应用顺序排列的已应用记录（ID、指纹、顺序位置）；
- 已应用变更**触及文件的“应用后镜像”**：完整行内容 + 逐行来源标记。
  未被任何已应用变更触及的文件不进镜像，续跑时直接读基准磁盘。

镜像让续跑**不必对磁盘做启发式补丁重放**，因此“链式修改（后一变更又改了
前一变更写入的行）”“崩溃窗口”等现场都能逐字、确定性地重建应用后视图。

为保证“**绝不重复应用**”，每个变更在 apply 时按以下顺序执行：

1. 全部文件补丁在内存中干净通过；
2. 把“已应用”记录与本变更产生的文件镜像加入状态，**先**原子持久化状态文件
   （临时文件 + rename）；
3. **再**把文件内容落盘。

续跑 / 重复提交时：

- 引擎只承认 SetID 相同的状态；其它变更集的状态被忽略（日志说明）。
- 以镜像直接重建内存文件视图（含逐行来源，冲突归因不丢失）。
- apply 模式对镜像覆盖的文件做**一次性磁盘对账**：内容一致不写；不一致
  （崩溃在“状态已写、文件未刷”窗口）则幂等补刷/补删除。该操作不重跑变更、
  不改状态。dry-run 只重建视图，绝不写盘。
- 随后逐个变更处理：已应用项按 **ID 或内容指纹**判为 `skipped`（不重复应用），
  未完成项从正确顺序位置继续；整个过程不重复应用、不静默丢失。
- 跳过判定、续跑对账与冲突定位均写入日志，包含变更标识与判定依据。

## 5. 结论报告（Report）

CLI 在标准输出打印 JSON 报告（日志走标准错误）：

- `mode`、`order`（判定顺序）；
- `results[]`：每项含 `id`、`status`（`applied`/`skipped`/`conflict`）、
  `reason`、`conflicts[]`（冲突位置与来源）；
- `rejected`：非空表示在归一/顺序判定阶段被整体拒绝，含可区分的 `reason`。

退出码：

| 码 | 含义 |
| --- | --- |
| 0 | 全部应用（允许有 skipped），无冲突 |
| 1 | 存在冲突 |
| 2 | 变更集被拒绝（归一/顺序判定失败） |
| 3 | 运行时错误（IO、状态损坏等） |

## 6. 验证方法

沿用仓库既有的 Go 构建与测试约定（无外部依赖）：

```bash
# 构建
go build ./...

# 静态检查
go vet ./...

# 全部单元测试与集成测试（含磁盘工作区与 CLI 子进程用例）
go test ./...

# 仅跑快速用例（跳过构建 CLI 子进程的用例）
go test -short ./...

# 查看包含变更标识、判定依据、冲突位置的详细日志
go test ./pkg/integrator/ -run TestEngine_Conflict -v
```

测试覆盖的关键场景（见 `pkg/integrator/*_test.go`）：

- **冲突**：上下文不一致、来源变更指认、多候选定位歧义、新建已存在文件、删除缺失文件；
  冲突后已应用变更不回退、后续变更不被静默处理；
- **重复提交**：同 ID 重复、不同 ID 同内容指纹、整集重复提交全部跳过、跨变更集状态不误跳；
- **中断续跑**：落盘后中断、“状态已写/文件未刷”崩溃窗口、从正确位置继续、
  幂等补刷、不重复应用；
- **稳定性与可区分性**：dry-run 与 apply 结论一致、结论与提交顺序无关、
  四类拒绝原因可区分。

### 命令行手动验证

```bash
# 1) 预演（不改动文件，结论 JSON 输出到 stdout，日志到 stderr）
go run ./cmd/integrator -mode dry-run -root /path/to/worktree -file changes.json

# 2) 实际应用（写入文件与 .integrator-state.json）
go run ./cmd/integrator -mode apply -root /path/to/worktree -file changes.json

# 3) 再次应用同一变更集 → 全部 skipped，退出码 0
go run ./cmd/integrator -mode apply -root /path/to/worktree -file changes.json
```
